Reliability · Controla-VA

A 17-minute session billed as 16.5 hours

Problem
A worker tracked 17 minutes and closed their laptop; by morning the session read 16.5 hours. Open sessions were billed as now − start, so any agent that died without a clean stop kept billing.
Approach
Billed time now has to be backed by evidence. A server-side clamp caps each session at its last recorded activity plus a grace window, and a reaper closes sessions whose agent has gone quiet. I later closed a second path where late offline data re-billed dead gaps, and designed an event-sourced model in which billed time is the union of verified intervals.
Result
Every installed agent version was corrected at once, without a client update. Under the new model, phantom hours can't be billed at all.
AI · Controla-VA

Keeping AI matching costs flat as data grows

Problem
Matching jobs to candidates meant an LLM scoring every CV in a keyword category. Cost grew with every upload, and keywords missed obvious matches such as "ML engineer" against "machine learning".
Approach
Retrieve, then rank. Each CV is embedded once into pgvector with an HNSW index, each job retrieves its nearest candidates, and only that shortlist goes to the LLM. Keeping vectors in PostgreSQL meant one query next to the existing filters and no new infrastructure.
Result
LLM cost per scan depends on the shortlist size, not on how many CVs exist. Candidates also surface for related roles they never applied to.
Desktop · Controla-VA

One desktop agent, about 50 machines, three operating systems

Problem
The agent runs on machines I can't touch. It has to survive sleep, crashes, power cuts and bad networks, update itself, and never lose or double-count paid time.
Approach
Electron with native modules. Every sample gets a client-generated ID, so the offline queue can retry safely. Updates install silently from a versioned channel, and the server enforces a minimum version. Browser URLs come from C# UI Automation over FFI. For macOS and Linux, a build-time platform layer keeps each bundle free of the other systems' code.
Result
The fleet updates itself, and most fixes ship on the server without a new build.

Data tooling · Bitnine Global

An extensible Oracle-to-PostgreSQL migration tool

Problem
Moving schemas and data from Oracle to PostgreSQL by hand is slow and error-prone. The DDL syntax, data types and conventions all differ.
Approach
A Python pipeline in three stages: extract the source DDL, transform it for the target schema, then move the data. One core sits behind both the CLI and the desktop GUI, and source-specific logic is kept separate so DB2 and MySQL can plug in.
Result
Full migrations run from one tool, and supporting a new database means writing a module rather than changing the core.
