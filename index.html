Reliability · Billing

A 17-minute session billed as 16.5 hours

The problem
A worker tracked 17 minutes and closed their laptop; by the next morning the session read 16.5 hours. Every read path billed an open session as now − startedAt, so when the agent died without a clean stop (shutdown, crash, dead battery, lost network), the session kept billing the whole time it was off. The server held bad data; this wasn't a display bug.
What I did
I changed the rule: billed time has to be backed by evidence, not by the absence of a stop event. Built a server-side clamp that caps a session at its last activity evidence plus a grace window, and a 60-second reaper that closes sessions whose agent has gone silent. Two months later a second cause appeared: late-arriving offline evidence was stretching closed sessions across dead gaps. I gave that path a floor as well as a ceiling. Then I designed an event-sourced model where billed time is the union of verified intervals, and ran it in shadow mode against the live numbers.
Outcome
Fixed server-side, so every installed agent version was corrected at once with no client update. A later re-check on production found every long session backed by continuous activity evidence. In the new model, double and phantom billing are impossible by construction.
Root-cause analysis NestJS PostgreSQL Event sourcing
AI · Cost at scale

Keeping LLM matching costs flat as the database grows

The problem
The recruiting tool matched jobs to candidates by having an LLM score every CV in a keyword-matched category. Cost grew with every CV uploaded, and keyword filters missed obvious matches ("ML engineer" vs. "machine learning"), as well as people whose CV was uploaded for a different but related role.
What I did
Built retrieve-then-rank. Each CV is embedded once, on upload, into PostgreSQL with pgvector and an HNSW index. A job retrieves its nearest candidates by cosine distance, and only that shortlist goes to the LLM for structured scoring, with the results persisted. The same index runs the other way, surfacing open jobs for a new candidate. I chose pgvector over a dedicated vector database: at this scale it's one SQL query next to the existing filters, with no new infrastructure. The old category scan is kept as a fallback, so a scan never returns nothing.
Outcome
LLM cost per scan is fixed by the shortlist size, not the database size. Matching is now semantic, so candidates surface for related roles they never applied to. Embedding a CV costs a fraction of a cent, once.
RAG pgvector / HNSW OpenAI embeddings Structured outputs
Desktop · Distributed systems

Shipping a desktop agent to a live fleet

The problem
A tracking agent on ~50 machines I can't touch, spread across Asia and Latin America, has to survive sleep, crashes, power cuts and flaky networks. It has to update itself without IT support, and it must never lose or double-count a minute that someone gets paid for. Then it has to run on macOS and Linux too.
What I did
Electron with native modules for input hooks, the OS keychain and image processing. It's offline-first: every sample carries a client-generated ID, so retries are idempotent on the server. Silent auto-updates come from a versioned release channel on Cloudflare R2, and the server enforces a minimum agent version, so stale builds are told to update instead of writing bad data. The active browser URL is read through C# UI Automation over FFI, capturing the site for ~95% of browsing time. As a rule, a fix goes on the server whenever it can, so it reaches every installed version at once. For macOS and Linux, a build-time platform layer strips every other OS's code from each bundle. macOS builds as a DMG in CI. Linux targets X11 first, then Wayland through a GNOME Shell extension.
Outcome
The fleet upgrades itself through the release channel, a server-enforced minimum version retires old builds, and most fixes ship with no new build at all. When "tampering" alerts turned out to be power cuts (confirmed from Windows crash events), I anchored the trusted clock to the OS boot ID on all three platforms.
Electron Offline-first Idempotency Auto-update
Security · Infrastructure

Trusting a client IP across four hops

The problem
The audit log recorded a Docker container's IP for every action. A request travels browser → Cloudflare → Caddy → Next.js → API, so the API's peer is the web container. The obvious fix, trusting X-Forwarded-For, would let anyone write a fake IP into a security log. And behind Cloudflare, even the proxy's own header held the edge's IP, which geolocated to another continent.
What I did
The Next.js tier reads the visitor IP from Cloudflare's own header first, falling back through the proxy headers. It forwards that IP inward with a shared-secret internal header that is different per environment. The API accepts the forwarded IP only when the secret matches; otherwise it uses the socket address. The header is read in exactly one place, behind that gate. The audit log is append-only, has no foreign keys (so rows outlive deletions) and never stores secrets or payloads.
Outcome
A who-did-what trail with the real client IP that an external caller can't spoof. If the secret is missing, it fails safe: it falls back to the old behaviour instead of trusting user input.
Threat modelling Cloudflare Caddy Audit logging
Correctness · Time zones

Night shifts that vanished at midnight

The problem
On the first of the month, people who'd worked overnight had zero hours for the new day. Every report filed a session under the day it started, so a shift running 11 pm to 4 am counted entirely in the old month. The obvious fix, splitting at midnight, raises the next question: whose midnight? The team spans Guatemala to Karachi.
What I did
I set the rule that a worker's hours belong to the day they were worked on their own clock: the agent's time zone first, then the office's. Reads became overlap queries that clip each session to the window, with a short look-back so sessions that started before the window are still found. Day, week and month boundaries are computed per zone in a DST-safe way, and every window end comes from the same start-of-period function, never from calendar math. One more trap: timestamps were stored without a time zone, so every conversion is explicit.
Outcome
A Karachi night shift now splits at Karachi midnight. A Guatemala shift that looks like it crosses midnight in Karachi stays whole on its own day. Billing-sensitive reports were left on the old convention on purpose, behind a single seam, until finance signs off.
Time zones SQL DST Domain modelling
Data engineering · Finance

Reconciling money across six sources and two languages

The problem
The company's month-end was a spreadsheet stitched from bank exports (in Hebrew), PayPal, Payoneer, Airwallex and eBay statements, in several currencies. Every source has its own format, quirks and ways of hiding the same transaction twice.
What I did
Built an import-and-reconcile platform: per-source parsers, rule-based classification that learns from manual decisions, invoice matching, VAT and a three-tier P&L. Then I hunted the edge cases: · One bank's credit column header contains another bank's header as a substring, so a header test silently read every outgoing payment as zero. Layout is now detected from the header, not the file extension, and an unreadable amount is flagged, never booked as 0. · A rounding fix that "worked" came back on re-import, because the import path ran its own raw SQL. The lesson: a data migration is never a fix on its own. · The same payment listed as Pending and Completed was being summed twice; partial card funding was being read as the price.
Outcome
Months reconcile to the cent at exact-precision FX. Each fix is pinned by a test against the SQL the database actually receives, and a grounded AI assistant answers finance questions from the ledger without inventing numbers.
ETL Multi-currency PostgreSQL LLM grounding
